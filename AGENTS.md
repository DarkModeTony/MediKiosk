## 1. Project Overview
- **Name**: MediPlatform
- **Goal**: An AI-powered clinical intake and medical record preparation platform for high-volume Indian hospitals.
- **Problem**: Doctors spend excessive time documenting patient histories in crowded OPDs, reducing actual diagnostic time.
- **Solution**: A smartphone-less Patient Kiosk collects history and documents before the doctor visit. The backend uses Gemini to OCR documents, extract structured entities, detect red flags deterministically, and generate an AI clinical summary for the doctor to simply review, edit, and verify.

## 2. Technology Stack: What is used & How it is used

### A. Backend Core
- **FastAPI (Python 3.14.7)**: Acts as the central orchestrator. It exposes RESTful endpoints (e.g., `/api/v1/clinical`, `/api/v1/documents`) that the frontends consume.
- **SQLAlchemy & Alembic**: SQLAlchemy acts as the ORM to interact with the PostgreSQL database. Alembic tracks database migrations in `backend/alembic/`.
- **AnyIO & Starlette**: Used inherently by FastAPI for async concurrency, essential for waiting on AI model responses without blocking the server.

### B. Database Layer
- **Supabase (PostgreSQL)**: Serves as the primary persistence layer.
- **How it's used**: We do NOT use the Supabase client SDK for data operations. Instead, we connect directly to the PostgreSQL instance using SQLAlchemy via a standard `DATABASE_URL` connection string (e.g., `postgresql://user:pass@host:5432/db`).

### C. Frontend Layer (Next.js 14+)
- **Two Separate Applications**:
  1. `frontend/patient-kiosk`: A highly interactive, touch-friendly UI for patients in the waiting room.
  2. `frontend/doctor-dashboard`: A dense, data-rich UI for doctors to review queues and verify clinical summaries.
- **TypeScript & Tailwind CSS**: Used for strict typing and rapid UI styling.
- **How it connects to the Backend**: The frontends use `fetch` wrappers inside `src/lib/api/` (e.g., `client.ts`). They read the `NEXT_PUBLIC_API_URL` to route calls to the FastAPI backend. If `NEXT_PUBLIC_DATA_MODE=api`, they strictly require the backend to be running.

### D. AI Layer (Google Gemini)
- **Model**: `gemini-3.6-flash`.
- **How it's used**: The `google-genai` SDK is used inside the `ai/` directory. The application abstracts the AI behind Provider interfaces (`OCRProvider`, `SummaryProvider`, etc.). Based on the `.env` variables (`AI_MODE`, `OCR_MODE`), a Factory class injects either a `MockProvider` (returns hardcoded JSON) or the `GeminiProvider` (makes real HTTP calls to Google).

## 3. Database Schema Deep Dive (SQLAlchemy)

The database schema is defined in `backend/app/models/models.py`.

### Core Entities & Relationships
1. **`patients`**: Stores the root identity of the patient. Uses a `JSONB` column `demographic_data` to store name, age, gender, and contact info flexibly.
2. **`encounters`**: The central transactional record. One patient can have many encounters (visits). It tracks the `status` (`IN_PROGRESS`, `WAITING_FOR_DOCTOR`, `COMPLETED`).
3. **`kiosk_sessions`**: When a patient starts the Kiosk, a UUID `session_token` is generated. This table links the transient kiosk session directly to an active `Encounter`.
4. **`clinical_histories`**: Linked to an `Encounter`. Stores the raw Q&A conversation data generated during the Kiosk interaction in a `JSONB` column.
5. **`red_flags`**: Linked to an `Encounter`. **CRITICAL RULE**: These are generated *deterministically* by backend rules (NOT by AI). It tracks `rule_name` (e.g., "Severe Chest Pain") and `severity` (`HIGH`, `MEDIUM`).
6. **`documents`**: Tracks files (images/PDFs) uploaded by the patient. 
   - **`document_ocr`**: Holds the raw transcribed text (`raw_text`) generated by the Gemini Vision model.
   - **`document_entities`**: Holds the structured medical facts (Medication name, Dosage, Diagnosis) extracted by the Gemini Extraction model.
7. **`clinical_summaries`**: Stores the AI's generated draft (`draft_content` JSONB).
8. **`summary_verifications`**: Created when the doctor hits "Verify" on the dashboard. It copies the draft, applies the doctor's edits, and saves it as `final_content` (JSONB).

## 4. End-to-End Pipeline: How Data Flows

### Phase 1: Registration & Kiosk Flow
1. Patient arrives and uses the Kiosk (`frontend/patient-kiosk`).
2. The UI sends a `POST /api/v1/patients/register` request to FastAPI.
3. FastAPI creates a `Patient` in PostgreSQL and creates a `KioskSession`.
4. The Kiosk UI receives the `session_token` and uses it to authorize subsequent API calls.

### Phase 2: Interactive Clinical Intake
1. The Kiosk prompts the patient with questions (e.g., "Do you have chest pain?").
2. The UI sends answers to `POST /api/v1/clinical/progress`.
3. FastAPI routes the answers to `ai/question_engine/engine.py`, which traverses hardcoded clinical pathways to determine the next question.
4. FastAPI simultaneously routes the answers to `ai/red_flags/engine.py`. If the patient indicates severe symptoms, a `RedFlag` is saved to the database.

### Phase 3: Document Processing Pipeline
1. Patient takes a photo of an old prescription and uploads it.
2. Kiosk calls `POST /api/v1/documents/upload`.
3. The image is saved locally in `backend/uploads/` (ignored in Git).
4. FastAPI triggers `ai/ocr/gemini_provider.py` which passes the image to Gemini Vision to extract raw text.
5. The raw text is then immediately passed to `ai/medical_extraction/gemini_provider.py`. Gemini is prompted with a strict JSON schema to identify medications, vitals, and diagnoses, assigning a `confidence_score` and `source_text` provenance to each.

### Phase 4: AI Summarization
1. The Kiosk completes the intake. FastAPI triggers `ai/summarization/gemini_provider.py`.
2. The provider aggregates the `clinical_histories` (Q&A), `document_entities` (extracted medications), and `red_flags`.
3. Gemini generates a unified, structured Clinical Draft Summary.
4. An aggressive validator (`ai/summarization/validator.py`) checks the output. If the AI hallucinates a medication not present in the source data, the validator strips it out or rejects the summary.

### Phase 5: Doctor Verification
1. The Doctor opens `frontend/doctor-dashboard`.
2. The UI fetches `GET /api/v1/encounters/active`. The backend sorts encounters based on the severity of their `RedFlags`.
3. The Doctor selects a patient and views the AI's Draft Summary alongside the original uploaded documents.
4. The Doctor edits the summary if needed and clicks "Verify". The backend saves this to `summary_verifications`. **The AI is purely an assistant; the human doctor is authoritative.**

## 6. Strict Hard Constraints for Agents
If you are an AI agent modifying this codebase, you **MUST** adhere to the following:

1. **Python Version**: **Do NOT downgrade Python from 3.14.7.** Do NOT attempt to install Python 3.10.
2. **Infrastructure**: Do NOT containerize the backend with Docker. Do NOT redesign the modular FastAPI/Supabase/Next.js architecture into microservices.
3. **Security & PHI**: Never commit real patient data, credentials, or `.env` files. `backend/uploads/` is strictly `.gitignore`d.
4. **AI Abstraction (The Factory Pattern)**: Always maintain the Provider interfaces (`OCRProvider`, `SummaryProvider`). Keep both Mock and Real providers intact. **Mock providers are mandatory for local development when Gemini API quotas are exhausted or internet is down.**
5. **Clinical Safety Boundaries**: 
   - Red-flags MUST remain backend authoritative (no frontend-only checks).
   - Summaries MUST be manually verifiable by a doctor.
   - Do NOT weaken the evidence validation logic (`validator.py`).
6. **Testing**: After modifying backend code, always run `python -m pytest backend/ -v`. Do not push broken code.

## 7. How to Execute Common Tasks

### Testing Backend
```bash
cd backend
source .venv/bin/activate # or .venv\Scripts\activate on Windows
python -m pytest backend/ -v
```

### Running the E2E Smoke Test
If the Gemini API key has quota:
```bash
cd backend
python smoke_test_full_e2e.py
```
*Note: If you hit a `429 RESOURCE_EXHAUSTED` with `free_tier_requests`, the daily limit is exhausted. Switch to `AI_MODE=mock` in `.env` to test without quotas, or wait until midnight Pacific Time.*

### Running Frontends
```bash
# Terminal 1
cd frontend/patient-kiosk && npm run dev
# Terminal 2
cd frontend/doctor-dashboard && npm run dev
```

### Modifying Providers via `.env`
The architecture routes traffic based on these `.env` variables:
- `OCR_MODE`: `mock` or `gemini`
- `LLM_PROVIDER`: `mock`, `gemini`, or `openai`
- `AI_MODE`: `mock` or `real`
